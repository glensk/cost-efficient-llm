\(\text{ITE} = \text{in} + 1.25\,w_{5m} + 2\,w_{1h} + 0.1\,\text{read} + 5\,\text{out}\)

ITE = input-token equivalents: how many fresh input tokens cost the same. \(w_{5m}, w_{1h}\) = tokens written to the 5-minute / 1-hour cache.

Say: Everything in this talk is in one unit, ITE: "how many fresh input tokens would cost the same". Claude Code caches almost everything, so fresh input is only the yardstick. Main sessions keep the cache 1 hour (write 2×), subagents 5 minutes (1.25×).

05 · every token pays rent

A token is written once, then paid again on every request.

tool call: output 5×→ tool result: written once 2×→ then 0.1× on every later request cost per token \(= 2 + 0.1 \times\) requests still to come

A 10k file read early in a long session costs 120k. Read narrowly: early is expensive.

Say: The tool call the model writes is output, 5×. The tool result, say a 10k file, is written into the cache once at 2×: 20k. From then on every request re-reads it at 0.1×: 1k each. After 20 requests the rent has cost as much as the write; after 100 it is 120k, six times the write.

Arithmetic from the price ladder (slide 3), main session (1-hour cache). The 10k / 100 requests example is illustrative; a median interactive session has 53 requests (decide API), long ones several hundred.

06 · why long sessions explode · model: re-reads and relay fees only

Context grows in a line. The bill grows in a parabola.

Double the session, 4× the re-read bill. A relay turns the parabola back into a line.

Say: Left, the context grows by about 1.8k per request; at 1M, today's context window, that is 522 requests. Right, the sum of all re-reads: every request re-reads a bit more than the last, so the sum is a parabola. With a relay at 150k we restart at 50k and pay a fee each time: almost a straight line. Factor 4.4 at the end.

Model: c_k = c_0 + g k, c_0 50k, g 1.82k (mean growth per request, 3,586 work requests in 9 chains: relay-research 2026-11-02-main-handover-cost.md B3). reads(k) ≈ 0.1 c_0 k + 0.05 g k²: 27.4M ITE at k = 522. Relay at 150k back to c_0, fee r = 120k (fast-path relay, relay deck slide 8): 9 relays, 6.2M. Factor 4.4. Only re-reads and relay fees are counted; new tokens and output are the same either way. The studies distinguish s_0 (first request) and c_0 = s_0 + 9k.

3stay warm, never resume cold

Answer ten minutes later, pay 20×.

  • Batch follow-ups inside the hour
  • After a long break: a fresh session from a note, not --resume
  • Mid-session, do not change MCP tools, effort or thinking

After an hour away, a fresh session from a short note beats --resume by 10×.

Say: The cache lives one hour in a main session, five minutes in a subagent, and every request renews it. Reply at 55 minutes: 150k are re-read at 0.1×, 15k. Reply at 65 minutes: all 150k are written again at 2×, 300k, before the model reads your new sentence. A fresh session with a short note costs about 30k.

Sources: TTLs and prices: Anthropic prompt-caching docs; 1-hour main / 5-minute subagent: transcript check 2026-11-10. 30k = measured warm session start 30.1k (slide 9). The docs list changes to tool definitions, thinking and effort settings as cache invalidators; a model switch is not listed there, so it is left out. Editing CLAUDE.md makes the NEXT session write it again. Refresh of the 2026-08 talk slide 2 (which showed $0.08 vs $1.50 on Opus 4.6).

4one task, one session

A new topic in an old session pays rent on the old one.

When the topic changes

  • /clear or a new session
  • Carry over only a short note
  • /compact = a built-in relay: automatic, but lossy

One task per session: /clear when the topic changes.

Say: Every request pays 0.1× its whole context. At 40k that is 4k per request; if the same small task runs at the end of a 150k session, every request pays 15k, mostly for a topic you finished an hour ago. /compact summarises in place: it is a relay done by Claude Code, cheaper than nothing but you do not control what survives. Skip if short on time.

Arithmetic: 0.1 × context (relay deck slide 5; agent-band.md Q1: 20-40k pays 2-4k, 110k 11k, 180k 18k per request).

5feed the context sparingly

What enters the context stays and pays rent.

What bloats a researcher's context

  • Notebooks with outputs and images
  • Printed dataframes and arrays
  • Full logs and training output
  • Whole-file reads for one function
  • Long answers and full rewrites (output 5×)

Ask for this instead

  • Read line ranges; grep with a cap
  • df.head(), shapes, summaries
  • Pipe noisy commands through tail -n 40
  • Strip notebook outputs before reading
  • Ask for a diff, not a rewrite

Every 10k you let in early costs ~120k by the end: print little, read narrowly.

Say: Slide 5 in practice. Whatever a tool prints lands in the context, is written once and re-read on every later request. A notebook with base64 images or a 5,000-line log is the classic. Ask the agent to look at line ranges, heads, tails, and to answer with diffs.

120k = 10k × (2 + 0.1 × 100 later requests), slide 5, illustrative. For notebooks: nbstripout or jupyter nbconvert --clear-output before the agent reads them.

6delegate to subagents · lean and BIG

Let a helper do the reading. Keep only its report.

Lean by default (a custom agent in .claude/agents/ that skips the instruction files). BIG only when the task needs your full rules, its tools or your judgment.

Send the reading to a lean helper; only its report enters your context.

Say: A subagent is a fresh session for one job. A lean one starts at 9k, so each of its requests re-reads under 1k, while the same work in my main session would re-read 4-15k per request. And my main session only receives the short report, not the twenty files the helper read.

Sources: lean 9.3k (median successor start, agent-band.md Q1), BIG ~32-35k (Q1 / cc_relay.py DEFAULT_AGENT_S0 35k), main ~41k start (decide API median of 178 interactive sessions, 41.05k) and ~133-176k at the relay. Re-read = 0.1 × context. Lean = agent definitions with omitClaudeMd: true (~/.claude/agents/opus-builder.md, sonnet-builder.md).

7relay · hand over the baton

Write a note, start fresh, keep going.

~14 requestsuntil the fee is paid back
438relays in our sessions in 30 days
90%of them judged a good handover

A relay costs about one fresh start and pays back within ~14 requests.

Say: Like a relay race: the runner does not stop the race, she hands the baton to fresh legs. The old session writes a short note; a new session starts from it at about 41k instead of carrying 159k. The fee is about 120k, mostly the new session writing its start context; it is paid back after about 14 requests.

Sources: decide relay-cost API via scripts/relay_cost_stats.py (run 2026-11-19 12:17): 438 relays since 2026-10-20, median context at relay 159k, 84% fast path, 90% verdict good; median handover + tail 66k ITE (the new session's first request, ~30-69k, comes on top). Fee ~120k ITE / ~$0.40 and break-even ~14 requests: fast-path relays of 2026-11-03 (relay deck slide 8, n = 4; 104-132k, $0.37-0.45). Start 41k: median of 178 interactive sessions.

7when to relay · model, fast-path fee r = 120k

Too early is worst. A bit late is cheap.

Too early is worst, a bit late is cheap, never is +40%.

Say: Cost per request as a function of where you relay. Left: relay too early and the fee, mostly the new session writing its start context at 2×, is spread over few requests. Right: wait too long and the re-reads dominate. The bottom is flat: anywhere in the band costs at most 5% more. Our hooks never relay a main session below 150k, force at 350k, hard cap 400k; subagents warn at 110k, are due at 150k and forced at 165k.

Model: f = r/k + 0.05 g k + 0.1 c_0 with k = (c − c_0)/g, c_0 50k, g 1.82k, r 120k (fast-path fee; the studies' optimum 137k used the older fee 209k): minimum c* ≈ 116k, ≤ 5% band 94-150k. Measured replay of 9 real chains (whole bill, main-handover-cost.md B3): relay at 80k +14 to +42%, at 250k +7 to +9%, never (force at 450k only) +37 to +42%. Rules: cc_relay.py docstring (floor 150k, force 350k = min(350k, cap 400k − 50k)), subagent band 110 / 150 / 165k.

8right model, right effort · list price per million tokens

The same token costs 40× less on a small model.

Small model

Renaming, formatting, boilerplate, summarising a log, simple scripts

Big model, high effort

Design, debugging, analysis plans. Thinking is output: 5×. Turn it up only where it pays

Pay big-model prices for thinking, not for typing.

Say: Prices per token differ by a factor 40 between the big and the small model. Mechanical work does not need the big model, and thinking tokens are billed as output, five times input. Use /model and the effort setting deliberately. Skip if short on time.

Source: bin/ai_lib/llm_prices.py (mydotfiles), checked 2026-11-19: claude-opus-5-5 $4 in / $20 out / $0.20 cache read; claude-sonnet-5-5 $2 / $10 / $0.20; claude-haiku-5-5 $0.10 / $0.50 (higher tier above 100k prompt tokens: $0.50 / $2.50). Seat limits per model are not covered here.

9attack the plan before you build · the Codex debate

The cheapest token is the one for work you never do.

Flaw found in the plan: a few thousand tokens of debate.

Flaw found after the build: you pay for the build twice.

Let a second model attack your plan before a single line is built.

Say: Before a big build, Claude writes the plan and a different model, Codex from another vendor, attacks it: read-only, it questions the requirements themselves and hunts flaws. They go back and forth in rounds; an independent judge decides when they converge. The plan is revised before any code exists. A wrong requirement found here costs a few rounds of text; found after the build it costs the build, twice.

How it works: ~/.claude/skills/codex-debate/SKILL.md (judged Claude ↔ Codex debate, Codex read-only, rounds until the judge's verdict; mode plan for PLAN files). No counts shown: no cheap source of debate statistics. You can do the same by hand: paste your plan into a second model and ask it to attack, not to agree.
