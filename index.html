02 · where the tokens go · our last 30 days

97% of the tokens are re-reads. They are 48% of the bill.

Half the bill is re-reading the context on every request. Keep the context small and the cache warm.

Say: Almost every token is the model re-reading what it already saw. Re-reads are cheap per token, so by price they are about half; a third is writing new things into the context, the rest is output: answers, thinking and tool calls.

04 · the context · requests and asks

No memory: every request re-sends everything.

re-sent: cache read 0.1× new: cache write 2× output 5× sizes illustrative

You type 1 prompt, the agent makes ~25 requests, and each re-reads everything before it.

Say: Request 1 already carries tools, system prompt, instructions and your prompt. The model answers with a tool call; the tool runs; its result goes back in request 2, which re-sends everything again. Example: you type "What did Adam write in his mail?"; request 1 ends with the tool call "list mails", request 2 carries the list and ends with "read mail", request 3 carries the mail's text and gives the answer. Your one question is three requests here, in real sessions about 25. Bottom row: what each request costs. The write part depends on what is new; the read part only grows. In the first requests the write of new tokens dominates; by request 50 the re-read is the largest part, and by 200 it is almost everything.

Sources: ~25 requests per typed prompt = median of interactive sessions that record a prompt count (n = 11 of 178; pooled ratio 24.4), decide relay-cost API, scripts/relay_cost_stats.py, run 2026-11-19 12:17. Bar sizes illustrative (tools + system 12k read warm from earlier sessions, instructions 8k, prompts 2k, tool call 0.5k, tool result 6k, answer 1k). Definition of k_A here is an assumption to confirm. The two later bars (k = 50, 200) follow the slide-5 model: c_k = 50k + 1.82k k (141k, 414k), 1.8k new (written 2×) and 0.5k output (5×) per request; mean output per request in the 30-day data is 0.53k. k = 50: read 14.1k + write 3.6k + output 2.5k = 20.2k; k = 200: 41.4k + 3.6k + 2.5k = 47.5k.

05 · why long sessions explode · model: re-reads and relay fees only

Each request costs a little more. The session total grows in a parabola.

One request: a line. A session: a parabola, 3 to 4× per doubling. Relays make it a line.

Say: Left, the context grows by about 1.8k per request; at 1M, today's context window, that is 522 requests. One request pays a tenth of its context: that is the line on the left, and it is linear. But a session pays for every one of its requests, so the session total is the sum of all of them, the area under the line. A rising line makes a triangle: double the length, four times the triangle. With the 50k we start from, doubling a session costs 3.3 to 3.7 times as much. That is the parabola on the right. A relay cuts the triangle into small teeth: with a relay at 150k we restart at 50k and pay a fee each time, almost a straight line. Factor 4.4 at the end.

Model: c_k = c_0 + g k, c_0 50k, g 1.82k (mean growth per request, 3,586 work requests in 9 chains: relay-research 2026-11-02-main-handover-cost.md B3). reads(k) ≈ 0.1 c_0 k + 0.05 g k²: 27.4M ITE at k = 522. Doubling: reads(100) = 1.41M, reads(200) = 4.64M, ratio 3.3; reads(261) = 7.50M, reads(522) = 27.4M, ratio 3.65 (only the growth part, the triangle, quadruples). Relay at 150k back to c_0, fee r = 120k (fast-path relay, relay deck slide 8): 9 relays, 6.2M. Factor 4.4. Only re-reads and relay fees are counted; new tokens and output are the same either way. The studies distinguish s_0 (first request) and c_0 = s_0 + 9k.

3stay warm, never resume cold

Answer ten minutes later, pay 20×.

  • Batch follow-ups inside the hour
  • After a long break: a fresh session from a note, not --resume
  • Mid-session, do not change MCP tools, effort or thinking
  • Waiting on a long job, or back later today? A keep-warm timer pings before each hour ends: ~15k ITE per ping.
  • A cold resume (300k) = 20 pings = ~16 h: a session you still need is cheaper kept warm all day. If a short note is enough, start fresh instead (30k = 2 pings).

After an hour away, a fresh session from a short note beats --resume by 10×.

Say: The cache lives one hour in a main session, five minutes in a subagent, and every request renews it. Reply at 55 minutes: 150k are re-read at 0.1×, 15k. Reply at 65 minutes: all 150k are written again at 2×, 300k, before the model reads your new sentence. A fresh session with a short note costs about 30k. Waiting on a long job, a keep-warm timer fires before the hour is up (mine 50 minutes after the last request, only while the cache is still warm) and wakes the session for one tiny request, about 15k at 150k context, which renews the hour; it only pays off if you will come back to that session. One cold resume costs as much as 20 pings, about 16 hours of pings every 50 minutes, so a session whose full context you still need is cheaper kept warm through the whole working day (8 hours is about 10 pings, half a cold resume); if a short note is enough, start fresh after about 2 hours instead, 30k is the price of 2 pings.

Sources: TTLs and prices: Anthropic prompt-caching docs; 1-hour main / 5-minute subagent: transcript check 2026-11-10. 30k = measured warm session start 30.1k (slide 7). The docs list changes to tool definitions, thinking and effort settings as cache invalidators; a model switch is not listed there, so it is left out. Editing CLAUDE.md makes the NEXT session write it again. Keep-warm timer: mydotfiles dotfiles/claude/.claude/hooks/cc-keepwarm.sh (armed by keep-warm-guard.py; fires at newest API call + 3000 s, below the 1-hour TTL, only while a wake is still needed and the cache is warm); ping 150k × 0.1 = 15k vs cold 150k × 2 = 300k. Break-even: 300k / 15k = 20 pings; 20 × 50 min = 1,000 min, about 16.7 h; 8 h is about 10 pings = 150k; fresh session 30k / 15k = 2 pings. The comparison ignores that the 5-minute subagent caches are not kept. Refresh of the 2026-08 talk slide 2 (which showed $0.08 vs $1.50 on Opus 4.6).

4one task, one session

A new topic in an old session pays rent on the old one.

When the topic changes

  • /clear or a new session
  • Carry over only a short note
  • /compact = a built-in relay: automatic, but lossy

One task per session: /clear when the topic changes.

Say: Every request pays 0.1× its whole context. At 40k that is 4k per request; if the same small task runs at the end of a 150k session, every request pays 15k, mostly for a topic you finished an hour ago. And a new topic is not one request: every prompt you type becomes about 25 requests, one per tool call, and each of them re-reads the old topic. /compact summarises in place: it is a relay done by Claude Code, cheaper than nothing but you do not control what survives. Skip if short on time.

Arithmetic: 0.1 × context (relay deck slide 5; agent-band.md Q1: 20-40k pays 2-4k, 110k 11k, 180k 18k per request). ~25 requests per typed prompt: slide 4 source (median of interactive sessions with a prompt count, n = 11 of 178, decide relay-cost API). Per prompt: 25 × 4k = 100k, 25 × 15k = 375k ITE.

5feed the context sparingly

What enters the context stays and pays rent.

What bloats a researcher's context

  • Notebooks with outputs and images
  • Printed dataframes and arrays
  • Full logs and training output
  • Whole-file reads for one function
  • Long answers and full rewrites (output 5×)

Set it up once

  • nbstripout git filter: no notebook outputs
  • Scripts log to a file, print a summary
  • CLAUDE.md: cap greps, tail logs, diffs
  • Data and results outside the agent's repo
  • Print df.head() and shapes, not the frame

Every 10k you let in early costs ~120k ITE by the end, 12× its size: print little, read narrowly.

Say: A token is written once at 2× and then re-read at 0.1× on every later request (backup slide 17). Whatever a tool prints lands in the context, is written once and re-read on every later request. A notebook with base64 images or a 5,000-line log is the classic. The agent already reads code narrowly on its own; the bloat comes from what your files and scripts contain and print. So fix it once in the setup: strip notebook outputs, make scripts quiet, and put one standing line in the instruction file (cap greps, tail noisy commands, answer with diffs).

120k = 10k × (2 + 0.1 × 100 later requests), backup slide 17, illustrative. For notebooks: nbstripout or jupyter nbconvert --clear-output before the agent reads them.

6delegate to subagents · lean and BIG

Let a helper do the reading. Keep only its report.

Lean by default (a custom agent in .claude/agents/ that skips the instruction files). BIG only when the task needs your full rules, its tools or your judgment.

Send the reading to a lean helper; only its report enters your context.

Say: A subagent is a fresh session for one job. A lean one starts at 9k, so each of its requests re-reads under 1k, while the same work in my main session would re-read 4-15k per request. And my main session only receives the short report, not the twenty files the helper read.

Sources: lean 9.3k (median successor start, agent-band.md Q1), BIG ~32-35k (Q1 / cc_relay.py DEFAULT_AGENT_S0 35k), main ~41k start (decide API median of 178 interactive sessions, 41.05k) and ~133-176k at the relay. Re-read = 0.1 × context. Lean = agent definitions with omitClaudeMd: true (~/.claude/agents/opus-builder.md, sonnet-builder.md).

7relay · hand over the baton

Write a note, start fresh, keep going.

~14 requestsuntil the fee is paid back
438relays in our sessions in 30 days

A relay costs about one fresh start and pays back within ~14 requests.

Say: Like a relay race: the runner does not stop the race, she hands the baton to fresh legs. The old session writes a short note; a new session starts from it at about 41k instead of carrying 159k. The fee is about 120k, mostly the new session writing its start context; it is paid back after about 14 requests.

7when to relay · model, fast-path fee r = 120k

Too early is worst. A bit late is cheap.

Too early is worst, a bit late is cheap; relaying only at 1M adds ~135% to the whole bill.

Say: Cost per request as a function of where you relay. Left: relay too early and the fee, mostly the new session writing its start context at 2×, is spread over few requests. Right: wait too long and the re-reads dominate. The bottom is flat: anywhere in the band costs at most 5% more. Our hooks never relay a main session below 150k, force at 200k, hard cap 400k; subagents warn at 110k, are due at 150k and forced at 165k. The dots are the whole bill, not the curve height: relaying at 200k instead of the optimum costs about 6% more on the whole bill, at 300k 21%, at 500k 60%, at 1M 135%.

Model: f = r/k + 0.05 g k + 0.1 c_0 with k = (c − c_0)/g, c_0 50k, g 1.82k, r 120k (fast-path fee; the studies' optimum 137k used the older fee 209k): minimum c* ≈ 116k, ≤ 5% band 94-150k. The curve is only fee + re-reads per request (its height ratio at 1M is +354%); the dots are the whole bill (output and new writes included). Measured: replay of the 9 real chains (main-handover-cost.md B3, b_replay.py), re-run 2026-11-20 with fixed relay points and the force threshold raised above each point; whole bill vs. the best fixed relay point of the replay (130k / 150k for a 41k / 51k successor start), mean of the two starts: 200k +6% (+4 to +8%), 300k +21% (+18 to +23%), 500k +60% (+56 to +65%), 1M +135% (+127 to +143%); force at 450k only +45 to +53%. Rules: cc-relay.py -T (floor 150k, force 200k (CC_RELAY_FORCE; code default 350k), cap 400k), subagent band 110 / 150 / 165k.

8right model, right effort · list price per million tokens

The same token costs 40× less on a small model.

Small model

Renaming, formatting, boilerplate, summarising a log, simple scripts

Big model, high effort

Design, debugging, analysis plans. Thinking is output: 5×. Turn it up only where it pays

Pay big-model prices for thinking, not for typing.

Say: Prices per token differ by a factor 40 between the big and the small model. Mechanical work does not need the big model, and thinking tokens are billed as output, five times input. Use /model and the effort setting deliberately. Skip if short on time.

9attack the plan before you build · the Codex debate

The cheapest token is the one for work you never do.

Flaw found in the plan: a few thousand tokens of debate.

Flaw found after the build: you pay for the build twice.

Let a second model attack your plan before a single line is built.

Say: Before a big build, Claude writes the plan and a different model, Codex from another vendor, attacks it: read-only, it questions the requirements themselves and hunts flaws. They go back and forth in rounds; an independent judge decides when they converge. The plan is revised before any code exists. A wrong requirement found here costs a few rounds of text; found after the build it costs the build, twice.

How it works: ~/.claude/skills/codex-debate/SKILL.md (judged Claude ↔ Codex debate, Codex read-only, rounds until the judge's verdict; mode plan for PLAN files). No counts shown: no cheap source of debate statistics. You can do the same by hand: paste your plan into a second model and ask it to attack, not to agree.

backup · every token pays rent

A token is written once, then paid again on every request.

tool call: output 5×→ tool result: written once 2×→ then 0.1× on every later request cost per token \(= 2 + 0.1 \times\) requests still to come

A 10k file read at request 1 of 100 costs 120k ITE, 12× its size; read 10 requests before the end, 30k. Early is expensive.

Say: The tool call the model writes is output, 5×. The tool result, say a 10k file, is written into the cache once at 2×: 20k. From then on every request re-reads it at 0.1×: 1k each. After 20 requests the rent has cost as much as the write; after 100 it is 120k, six times the write. The same file read 10 requests before the end costs 20k + 10k = 30k.

Arithmetic from the price ladder (slide 3), main session (1-hour cache). The 10k / 100 requests example is illustrative; a median interactive session has 53 requests (decide API), long ones several hundred. Per token: 2 + 0.1 × later requests; at request 1 of 100: 2 + 10 = 12, 10k → 120k ITE (12× its size); 10 requests before the end: 2 + 1 = 3, 10k → 30k ITE.
